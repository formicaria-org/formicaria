# 2026-10-11 — tap to edit, v0.6.6, and updating on the desktop

A snapshot of the second half of one day, as believed then. For current fact read `features.md`,
`known-issues.md` (*Updating on the desktop*), `outstanding.md` (§2.19) and `decisions.md` (the
2026-10-11 entries).

## What was asked
- *Edit* under the ＋ is redundant on every system: a click on the note should start editing. Then,
  over three test builds: the caret is in the right place, but it should be **in the middle of the
  view**; and lower down a note the view went past it.
- *"I had to go through 0.6.3 before arriving at the latest and it fails."*
- *"All this copying and pasting by me can be done by you."*
- *"I see no button to check now and install on the desktop."* Then: *"we need a test to see if
  this feature is present and working."* Then: a copy built from source must be able to take the
  latest release, as it can on the phone.

## What was built
1. **Tap to edit**, with the caret on the tapped word and centred, and no *Edit* in the ＋.
2. **The updater's floor**: a test build is never offered a release older than the one it was built
   on; *Check now* beside an offer; a plain sentence for an older package.
3. **`pixi run -e android phone-test`**: the Android workflow, its artifact, the certificate check
   and the install, in one command. Not yet run end to end (it needs a token).
4. **v0.6.6**, tagged after the owner confirmed the caret on the phone.
5. **`pixi run update-test`**, and `update-test.yml` for the three desktop systems.
6. **A copy built from source installs the release** into `target/app/`, through the existing
   swap. The owner did it for real within the hour.
7. **The page reloads after a restart**, which it had always claimed to do.

## What went wrong, and what it taught
- **The caret was centred to the pixel in the browser and wrong on the phone.** An error that grew
  with distance down the note was a measuring error: the likeness of the textarea did not wrap like
  the textarea. Measuring in a copy of the element itself ended it. **When a device disagrees with
  a simulation, stop refining the simulation and measure with the thing itself.**
- **"No update buttons" was diagnosed as "your program is old", which was true and beside the
  point.** The owner's complaint was that the desktop behaved differently from the phone. The first
  answer defended a ruling two days old (*a source copy may look, not install*) instead of noticing
  that the owner had just contradicted it. **A report that contradicts a ruling is a reason to ask
  whether the ruling still stands, before explaining it.**
- **The first hand test opened a browser tab and wrote into the owner's real update settings.**
  The app opens a browser by default and keeps settings per machine. The scripted test gives the
  copy a home of its own and turns the browser off.
- **A sentence nobody had made true.** *This page reconnects by itself* had been on screen since
  the updater shipped, and no test or run had ever waited to see it happen. The real install found
  it in a minute.
- **A guard that would have forced a lie.** Every release job had to be `continue-on-error`, which
  would have turned a failing update test green. The guard now exempts jobs that run after
  publishing, and the reason is beside it.
