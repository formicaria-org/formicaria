# 2026-07-17 — Track C Phase 1: one shared vault actually works

**Outcome:** all five Phase 1 items in [`plan.md`](../plan.md) are implemented and
regression-tested; `pixi run ci` green. Verified as a **real round trip** — two vaults, a
bare remote, everything through the HTTP API: they push → `ls-remote` notices → we edit a
*different paragraph of the same note* → `pull` merges clean → both edits are in the note
and visible in the index → we push back → their clone pulls ours. The plan's own bar —
*"two clones edit different lines of one note → clean auto-merge, no `updated:` conflict.
That is the test that says shared vaults work"* — passes.

Follows `2026-07-17-phase-0.md` in the same sitting. Phase 2 (multi-vault + the rename) is
next.

## What landed

- **The `FileStore::put` staleness guard** — *the* lost-update bug. Every writer above
  `put` is a read-modify-write over `Store::get`, which serves **SQLite, not the file**, so
  once anything else writes a note the app holds a stale copy. `set_property` was the
  vicious one: a board drag rewrote the whole file, body included, from that stale copy —
  and the user never thought they were writing prose. One guard (indexed `mtime_ns` vs the
  file's) covers both writers and every future one, and keeps mtime out of the `Store`
  trait. New `StoreError::Conflict(Id)`, which also renders without `Io`'s `io error:`
  prefix.
- **Incremental reindex** — reconciled by **path**, not id (a note's id is in its
  frontmatter, so the two can disagree). Re-reads only what moved; reports `removed`
  separately from a *failed parse*, because a note that never parses would otherwise
  report "changed" every 3 s forever and the UI would refresh in a loop.
- **The 3 s local poll** — folded into the `ping` heartbeat that already beat at exactly
  that cadence, so it costs one incremental reindex rather than a second timer and a second
  round-trip. Without it a pull is *invisible*: the views are served from SQLite and a full
  reindex only ran at `open`.
- **`ls-remote` remote poll + `pull`** — `git::remote_moved` asks whether they pushed
  **without fetching**, which matters: fetching is what advances the tracking ref, and an
  advanced tracking ref is precisely what Phase 0's ancestry guard exists to survive. Ask
  first, fetch on purpose. `pull` merges through the driver and re-indexes; `Pulled` names
  each outcome because each is a different sentence to the user.
- **The `.md` merge driver** — `fm-core/src/merge.rs` + `fm merge-md`, installed by
  `ensure_repo`. See `decisions.md` for the full entry.
- **UI**: a "Get their changes" button, "Someone has pushed work you don't have yet" when
  `remote_moved`, and conflicted notes listed by name.

## Decisions made (folded into `decisions.md`)

- **Shell out to `git merge-file` for the body.** A 3-way text merge is solved; carrying a
  diff3 would be a new dependency and a new way to be wrong.
- **Never install a merge driver we cannot point at.** See the trap below.

## Traps found on the way — both by verifying, not by testing

- **A driver that can't run is worse than no driver.** The first cut pointed
  `merge.fm.driver` at a bare `fm` and let PATH answer. `fm` is not on PATH here (pixi
  only), so git ran a nonexistent command, read the non-zero exit as "conflict", and left
  `%A` **untouched** — ours, with **no markers**. The user resolves a perfectly
  normal-looking file and silently deletes their collaborator's edit. Caught because it
  broke `auto_commit_refuses_to_enshrine_conflict_markers`, which was *right to break*:
  it asserted markers exist, and they didn't. `merge_command()` now returns `None` unless
  a real binary sits beside the running one; no driver degrades safely to git's text
  merge. **This is the single most dangerous thing this session nearly shipped.**
- **The driver leaked its scratch filenames into people's notes.** `git merge-file` labels
  conflict markers with the file names it was given, so a real merge produced
  `<<<<<<< .fm-merge-294822-ours`. Fixed with `-L ours -L base -L theirs`. Only visible by
  running a real merge and *reading the note* — no assertion would have caught it.
- **And it wrote those scratch files into the repo.** `%A`'s directory turned out to be
  the vault, not a git temp dir; with `git add -A` firing every 5 s, a scratch file could
  have landed in someone's history. They live in `$TMPDIR` now.
- **`Object::new(kind, …)` takes the *body*, not the title.** Cost one wrong assertion.

## Left not-working

- **`remote_moved` is only consulted when the backup panel opens.** The plan's *automatic*
  15–30 s poll — be told someone pushed without going looking — is not wired. The cheap
  part (a `ls-remote` that moves no refs) exists and is proven; it needs a timer and a
  place in the chrome to show it.
- **Conflicted notes are listed only in that panel.** The driver's real gift is that
  markers land in the **body**, so a conflicted note opens in the editor and resolves in
  the textarea — but nothing points you at it unless you open the backup panel.
- **`FileStore::skipped()` is still stderr-only** (carried from Phase 0).
- **Panel errors still read `io error: …`** for every `StoreError::Io` (carried from
  Phase 0). `Conflict` avoids it by being its own variant, which is a hint at the fix: a
  `Refused(String)` variant with no prefix.
- **Tag deletion loses to tag addition.** Union means a tag one side deleted while the
  other kept it comes back. Deliberate — re-deleting is trivial, losing someone's tag
  silently is not — but it is a real asymmetry, written down here rather than discovered
  later.
