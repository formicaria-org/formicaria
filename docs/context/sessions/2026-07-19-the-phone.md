# 2026-07-19 — Step 0: the app, on an actual phone

**The first time any of this has been seen on a real device.** Step 0 of the corrected Track M
sequence — an hour, zero product code — executed end to end on the owner's phone
(a Dimensity 7300 device, 7.4 GB), against the real backend.

## The setup, and that it holds

`pixi run android-init` → project-local `platform-tools` r37.0.0 in a gitignored `.android/`,
SHA-256 verified. Android 11+ **wireless debugging** (pair with a code over Wi-Fi), then
`adb reverse tcp:8765 tcp:8765`, then `http://127.0.0.1:8765` in the phone's browser.

Confirmed working, and worth recording because each was a real question beforehand:

- **Nothing installed system-wide, and no USB.** No `sudo`, no udev rule, no `plugdev`
  membership — the toolchain is a zip in the tree and the device link is Wi-Fi.
- **Nothing listens on the phone.** `adb reverse` tunnels the phone's own localhost to the
  host, so the device sends `Host: 127.0.0.1:8765` and every guard in `fm-serve` passes **by
  construction, zero lines changed**. The Android-loopback trap in `known-issues.md` is avoided
  rather than mitigated.
- **It is the real thing.** `pixi run serve` builds the PROD bundle, so `import.meta.env.PROD`
  is true: real `dispatch`, real `blob.rs`, hashed assets — not `ui/src/lib/mock.ts`.

Two traps found by walking into them, both now documented in `mobile-design.md` and in the text
`android-init` prints:

1. **There is no `adb connect` step.** adb finds the device over mDNS and connects it itself the
   moment pairing succeeds. Running `connect` by hand races that, fails (the pairing dialog's
   port is *single-use* and differs from the one on the main Wireless-debugging screen), and
   leaves a dead entry — which makes every later command answer `more than one device/emulator`.
2. **A stale server reads as a UI bug.** The `fm-serve` that was running had been built the
   previous afternoon, so it predated the structured skipped-notes payload; `ping` came back
   without the field entirely while today's `ui/dist` expected it. Restart after backend
   changes — the reverse tunnel survives it.

## The finding

> **The current GUI is not good for small screens.** — the owner, first pass.

That is deliberately recorded as the coarse verdict it is: a first impression, not a defect
list. The specific items step 0 set out to settle — Board scroll-snap versus finger drag, the
tap→move menu, a `<video>` seeking mid-file (the only thing that exercises `blob.rs`'s `Range`
path on real hardware), Excalidraw under a finger, thumb reach on the 2.75rem targets — were
**not** individually reported, so they remain open.

## What it changes

**Packaging is not the next thing.** The plan had M0 (`cargo tauri android init`) behind step 8
(NDK, toolchain lock), and this says the gate above both of those is the UI itself: an APK
wrapping a shell that does not work on a small screen is a worse artifact than no APK, because
it makes the layout problem look like a mobile-platform problem. **The single-column touch work
— filed as M6 — moves ahead of M0 and step 8.** That inverts the plan's own ordering, and it is
exactly the kind of inversion step 0 existed to discover before anything expensive was built.

This also vindicates the sequencing: the review put step 0 first specifically because it needs
no NDK, no git backend and no decision, and it has now changed the plan before a line of Android
code was written.

**`outstanding.md` §1.1 is only *partly* retired.** The app has now been seen by eye on a phone,
which is more than was true this morning. The pane workspace on a desktop, and each of the
specific paths listed above, still have not been. Do not mark §1.1 done on the strength of this.
